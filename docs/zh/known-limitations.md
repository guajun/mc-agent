# 已知实验与分叉限制（Minecraft 26.2）

这里集中记录保真缺口和可用的实验边界，不承诺完整世界或 JVM 检查点恢复。
正式 Go CLI 尚未实现世界 `fork`／`restore`；实体 NBT／顺序只是世界分支的一部分。
参见[项目范围](concepts.md#world-forks-and-experiment-boundaries)。

## 先标记所需现场，再选择恢复配方

借用运维中的**检查点（checkpoint）**、**静止点（quiescent point）**和
**恢复配方（recovery recipe）**：分类对象是实验需要保留的现场，而不是给实体或
机器固定分级。这里“存档可存”指存档覆盖所选条件需要的数据，加载与重建仍需验证；
“存档不可存”指存档不足以精确恢复全部所需运行态，即使其中一部分数据已经持久化。

| 实验所需现场 | 内存条件易重建，有已验证的配方 | 内存重建困难、需要额外采集，或尚未验证 |
| --- | --- | --- |
| 存档可存 | 停止且收敛、所需基线可跨加载保留的机器；加载验证后再启动 | 所需数据已保存，但复杂内存成员／引用关系重建困难；验证加载与重建过程 |
| 存档不可存 | 实验允许从关机基线重放启动的机器；可用命令或预备红石电路重新生成所需顺序的实体 | 现有活塞运动相位、待执行事件顺序、精确随机轨迹，或现有配方无法重建的实体内存顺序；需要额外运行态采集／重建支持 |

矩阵和以下标签用于描述，不是互斥的等级。按组件、所需条件打标签，同一实验可以
同时带多个标签：

- **存档足够**：所选基线需要的条件可跨保存／加载恢复，并经过验证。
- **分叉前静止**：先关闭机构，让相关运动和更新收敛，再选基线；在分支中启动。
- **配方可重建**：记录的命令、输入、时序或生成电路可重建所需内存条件。
- **需要运行态采集**：存档与现有配方不足以恢复所需既有现场；注明采集范围和剩余缺口。

活塞、流体及随机性依赖机器的默认支持配方是：**关闭、收敛并验证 → 保存／分叉
→ 恢复并验证 → 在分支中启动**。运行过程中分叉可能改变机器行为或破坏实验，
当前不保证这类续演。“关闭”指游戏装置停机，不是卸载区块或关闭服务器。
关机不自动等于收敛：确认相关流体状态和待执行更新，记录启动输入与时序。
该配方不保留既有运行相位或精确随机流；若它们本身就是研究对象，不能用关机起点
偷偷替换。动态态直接分叉的支持可以以后逐步补足。

## 移动中的活塞与待执行方块事件

当前不保证从活塞移动中的状态分叉后精确续演。在 26.2 中，
`PistonMovingBlockEntity.saveAdditional` 把 `progressO` 写到 NBT 的 `progress`；
`loadAdditional` 从这个值恢复 `progress`，并让 `progressO` 等于它。
`lastTicked` 没有持久化。因此存档中的移动方块状态没有保留全部实时运动状态。
服务端待执行 block-event 队列及其顺序也没有被普通世界保存编码。
刻间边界不能证明队列为空：事件仍可能留到下一刻执行。

这是分支保存／加载的保真缺口。写出活塞 NBT 本身不会把源服活塞字段重置成加载后的值；
源服保存维护的影响与分支重建要分别评估。`save-all` 及其正常维护影响仍是项目接受的边界。

若实验可以从静止机构开始，可在干净基线分叉，然后在分支中启动活塞并完成测量，
不让进行中的运动跨越分叉。应验证基线的方块、朝向、时序和相关条件；仅看活塞静止
不能证明没有待执行方块事件。如果研究问题必须保留已经运行中的精确中间状态，
这个方法就不适用。直接从动态态分叉是未来逐步支持、逐项验证的目标。

## 实验中的实体生命周期

实体 NBT／顺序及按顺序逐个 summon 仍可用于恢复支持的实体。若实验允许每次试验
重新产生实体，并在测量期间持续保持 loaded／ticking，可在分叉后产生实体，在分支中
即产即用。验证相关身份／引用、顺序、运动和启动条件。这样可以避免让生命周期过渡
跨越分叉，但不覆盖依赖原实体历史或未支持运行态的实验。

若实验依赖实体运算顺序，应按已有准备和可用工具选择路径：

1. **Mod／CLI 辅助采集**：使用支持的实体 NBT／顺序采集，按记录顺序重建支持的实体；
   检查采集覆盖范围、引用和实际运算顺序。这不是完整内存检查点。
2. **Agent 自行重建**：通过能够可靠反映所需顺序的一般探测路径，记录实体数据和恢复
   配方，再通过存档及受控加载／生成过程重建。NBT 列表顺序或偶然的查询输出顺序，
   不能单独证明内存运算顺序；必须验证结果。
3. **玩家／电路重建**：手动按顺序生成实体，或运行已准备的红石生成电路；记录输入、
   时序和顺序，并验证生成后的基线。

这些路径可以组合。如果用户已经准备好能重建所需实体顺序的电路，就选实体生成前、
机器关闭的状态作为基线，恢复后运行该电路。此时任务可以回到静止点配方，不必保留
现有实体列表。若实验要求原实体及其历史，重新生成就不是等价路径。

## 水流与随机刻

水流并非保存后全部丢失：流体方块状态与计划执行的 `fluid_ticks` 会持久化。
26.2 水流使用计划流体刻（延迟 5），不是随机刻。保真仍取决于文件、内存和计划队列的
一致性、保存延迟的 gameTime 基准、跨区块顺序，以及实际 loaded／ticking 区块集合。
仅有持久化流体数据不能证明续演完全相同。

保存的计划刻保留各区块内的相对顺序，但没有编码原始跨区块全局 `subTickOrder`。
恢复同刻、同优先级的计划刻时，执行顺序因此可能改变。水流扩散本体使用计划刻，
破坏方块的掉落等次级行为仍可能消耗随机数。熔岩还有随机扩散延迟和随机刻点火，
需要另行评估。

随机刻有另一类缺口：用于选位置的 `Level.randValue` 和用于方块行为的 `Level.random`
的当前状态没有保存。世界重载会重建这些随机源；单个区块卸载本身不会重建整个 Level
的随机源。不过 ticking 集合与随机调用消耗改变仍可能改变轨迹。合理设计的统计实验
仍然可做，但不能承诺分叉后相同 seed 的下一次随机结果相同。

这些做法属于实验设计，不能悄悄改变研究问题，也不能把未支持状态说成精确续演成功。
