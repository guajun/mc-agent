# 整体结构

这是本项目最终收敛出的心智模型，以及由它推导出的规则。之所以要写下它，是因为这类代码库里绝大部分混乱，都来自把"**某个东西跑在哪里**"和"**它是什么**"混为一谈。

相关文档：[RFC 0001](rfc/0001-agent-interface.md)（接口与 bridge）、[RFC 0002](rfc/0002-programmable-tool-calls.md)（运行中注入代码）、[分叉一个活的世界](protocol-snapshot.md)、[智能体在游戏里是谁](player-identity.md)。

## 两个环境，以及它们之间的 bridge

| | 它是什么 | 它负责 |
| --- | --- | --- |
| **实验环境** | 智能体所在的地方：终端、文件、分析、审批、模型调用（本项目对着 Hermes 开发） | *判断力* —— 做什么、什么时候、用什么参数 |
| **生产环境** | 世界真正运行的地方：玩家的活客户端、别人的活服务端，或智能体自己拉起来的实例 | 世界本身，以及**只存在于它进程内**的事实 |
| **bridge** | 两者之间的接缝：组合与传输 | 把一堆 I/O 步骤变成**一个工具**，并搬运数据 |

bridge **不是**一个环境，也不是一条轨道。对着任何装了接口 mod 的实例，跑的都是同一个守护进程；轨道之间变的是**哪一个实例**，不是哪一份软件。

## 一项新能力该放进哪一层？

一条规则，然后看例子：

1. 能表达成"原语 + 等待 + 整形"？→ **bridge**。
2. 需要每个 tick，或需要只有游戏进程内才有的状态？→ **mod**。
3. 需要判断（要不要做、什么时候、用什么参数）？→ **智能体**。

| 能力 | 层 | 为什么 |
| --- | --- | --- |
| `mc_command_output`（发命令并收回答） | bridge | 两个原语加一次等待 |
| `mc_entities`（按类型计数 + 最近的 N 个） | bridge | 对 mod 已经报上来的数据做整形 |
| `mc_fork`（冻结、保存、快照、拷贝世界） | bridge | 对已有原语做有序编排 |
| `SNAPSHOT`（**按 tick 顺序**的实体集合 + NBT） | mod | 顺序是存档文件里没有的**进程内事实** |
| 热编译探针（延后，见下） | mod | 需要在进程内逐 tick 执行 |
| "这次跑得可不可复现、复现重要吗" | 智能体 | 这是判断，不是机制 |

其余的一切——分析、对比、世界文件手术、一次性脚本——都属于智能体自己的工具箱：一个终端和一个文件系统。本项目不去重造它们。

## 三条轨道：同一个 mod，三种实例

| 轨道 | interface mod 跑在哪 | 用来做什么 | 迭代成本 |
| --- | --- | --- | --- |
| **1. 探针**（延后） | 活实例，运行中编译 Java 并热替换 | 把逐 tick 的观测、计算、驱动放在同一个地方 | 秒级，不重启 |
| **2. 活服上的 mod** | 活实例，作为一个普通 Fabric mod——**也包括单机世界里的集成服务端** | **保真**：真实的实体顺序、在场的玩家、生物 AI 状态；以及任何需要 mixin 或注册新内容的事 | 一次构建加重启（约 1–2 分钟） |
| **3. 实验室** | 智能体自己供应的实例：一份复制的世界 + 一个无头服务器 | **可重复**：冻结 tick、逐步执行、批量运行；不需要人、不需要任何人授权、不动活的世界 | 秒级 |

轨道 2 不需要专门开服务器：单机里客户端 vantage **和**服务端 vantage 跑在同一个进程里（25580 与 25581），所以边玩就能做权威快照。

轨道 1 是**故意延后、且数据驱动**的：先把轨道 2 和轨道 3 跑起来，看哪些辅助**反复被手工补**，只有当同一种需求反复出现时，才值得做探针 SDK。它的天花板是真实的（不能 mixin、不能注册内容、不能改 vanilla 行为），它的便利也是真实的，所以这个决定应该由证据而不是热情来做。

## 大脑、手、身体

* **探针**（或脚本）是**大脑和手**：在一个 tick 内读、算、动手，不需要网络往返。
* **Carpet 假人**是**身体**：一个真正的 `ServerPlayer`，压力板会感知它、生物会仇恨它、区块会围着它加载、其他玩家能看见它。
* 两者是**组合**关系：代码可以召唤假人并按 tick 精确驱动它（比每 tick 敲一次 `/player <name> use` 高一个档），而任何依赖**"存在"**的效果依然需要那个实体，而不是代码。

读数据是另一半：客户端的视图是**为渲染插值**的（同一个起跳的假人，客户端读到 `vy=0.333`，服务端是 `-0.078`），所以**测量要放在服务端视角**。

## 为什么"分叉"需要两样东西，而不是一样

存档里有方块和实体的 NBT，但**没有实体的 tick 顺序**：`EntityTickList` 是一个插入有序的表，在区块加载时被重建；而这个顺序会改变任何"逐个实体计算"的结果——挤压、堆叠、爆炸。

所以"分叉一个活的世界"是两件事：

* **方块**：`/tick freeze` → `/save-all flush` → 拷贝世界文件；
* **实体 + 顺序 + 内存态**：一份进程内快照，并带 `orderHash`，这样还原可以被**校验**，而不是被相信。

它买到了什么、没买到什么：

| | 活实例（轨道 2） | 实验室（轨道 3） |
| --- | --- | --- |
| 实体顺序 | 真实演进出来的那一个 | 被记录、可复现，并且可以**规范化** |
| 观测 | 此刻正在发生的事 | 实验规定应该发生的事 |
| 可复现性 | 无法从存档复现 | 可复现，并由一次重新快照来验证 |

实验室无法把自己变得和活会话完全一致——但它可以记录那次会话的顺序、把它重放，并量化结果对它的依赖程度。

## 真正必须由我们写的

其余一切都交给智能体的终端和文件。

| # | 东西 | 为什么只有我们写得了 | 规模 |
| --- | --- | --- | --- |
| 1 | mod 的服务端入口 | 只有进程内才有那些事实 | S |
| 2 | `SNAPSHOT`：按 tick 顺序的实体、含 NBT 与顺序哈希 | 同上；存档记不下来 | M |
| 3 | tick 顺序观测（可选） | 进程内事实 | S |
| 4 | 无头实验室的供应 | 游戏知识：Fabric 服务端、mod 集合、首次启动的世界 | S-M |
| 5 | `mc_fork`：冻结 → 保存 → 快照 → 拷贝 | 带游戏知识的有序编排 | S-M |
| 6 | bridge 的可换后端（客户端 / 服务端 / 实验室） | 架构 | S |

技能与配方——怎么拿到世界副本、怎么起实验室、怎么做确定性步进——都是文档，是**做过一遍之后**写下来的。它们记录实践，而不是猜。

## 故意不做的（至少现在）

* 一个带大量类型化 host API 的脚本宿主（RFC 0002 的第一版草案）：为还没被证明的需求做太多设计。实测过的替代方案——全部从进程外做——大约是"看一眼 35 毫秒、一个 tick"，到目前为止所尝试的一切都够用。
* 在流程只跑过一次之前就写"skill"。
* 第三方脚本 runner（Minescript、Neo Scripts Lua）：形态不同（外部进程，或 GPL），只能当参考。
* 任何用例逻辑：核心里没有大炮、没有硫方怪、没有分析流水线。只对某一个实验重要的东西，就跟着那个实验走。
* 智能体侧不需要常驻守护：智能体可以启动某个东西、等一会儿、之后再回来。
* 不做沙箱：智能体写的代码是你自己游戏上的**可信本地代码**。护栏是预算、故障隔离和 kill 开关。

还没有定论的问题都收在 [issue 跟踪器](https://github.com/guajun/mc-agent/issues?q=label%3Arfc)里：RFC 0001 已实现并关闭，RFC 0002 已推迟（见上）。
