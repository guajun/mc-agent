# Minecraft 26.2 世界分叉：tick 边界、保存与运行态审计

审计日期：2026-10-04。状态：源码审计完成，运行验收未执行；本文不是已实现能力声明。

项目目标是把足以开展实验的世界分支带到 Agent / Harness 机器。第一阶段限定 Minecraft 26.2，在完整服务器 tick 的逻辑边界采集，不要求任意执行阶段或整个 JVM 检查点。保留运行态是“实验条件足够”的更强实现手段。

**当前接受正常 `save-all` / flush 引起的保存与维护副作用。** 不为采集主动卸载、重载源服仍是目标，但这不等于承诺生产保存路径绝不推进待卸载、待加载或任务。对保存敏感的实验，应从更早、经验证保存不会破坏相关条件的干净起点建立分支，再按操作序列推进。这是明确的实验设计边界，不要求支持任意时点透明分叉。短暂停顿及 CPU/IO 开销也不作零影响保证；具体采集实现尚未落地。

逐个 `/summon` 配合实体 NBT 重建仍是可用候选，不应因为不能覆盖所有运行态而被整体否定。审计需要明确它覆盖什么，以及世界分支还缺什么。相关设计背景见 [#40](https://github.com/guajun/mc-agent/issues/40)，工具链反馈见 [#51](https://github.com/guajun/mc-agent/issues/51)。

## 选定的逻辑边界与民间阶段映射

### 原生服务器循环

**实查**，26.2 正常运行路径的主线程顺序如下：

```text
MinecraftServer.runServer
  processPacketsAndTick（虚调用，含 IntegratedServer override）
    tickFrame.start
    packetProcessor.processQueuedPackets
    tickServer
      tickCount++ / tickRateManager.tick
      tickChildren
        commandFunctions.tick / clocks
        每个 ServerLevel.tick
          weather / sleep / tickTime
          blockTicks → fluidTicks
          raids → chunkSource（含随机刻、生成等）
          blockEvents
          entities → blockEntities
          entityManagement / debug
        connection → players → debug / gameTests / tickables / send chunks
      status / autosave / tallying
    tickFrame.end
    IntegratedServer override 尾部（gizmo 收集）
  ← 推荐采集入口：本次 processPacketsAndTick 返回后、waitUntilNextTick 之前
  waitUntilNextTick
    runAllTasks / managedBlock（会继续执行 server 与 chunk tasks）
  下一轮 processPacketsAndTick
```

推荐在 `runServer` 中 `processPacketsAndTick` 调用返回后建立采集入口，按该次循环、server tick counter、各维度 gameTime 记录时点。它位于完整服务器处理之后，覆盖所有维度及 integrated override，而不是某个维度结束。此时正常返回的计划刻执行、实体遍历、方块实体遍历和同步邻居更新链已结束，因而无需捕获它们的 Java 执行栈或正在消费的临时队列。异常 tick 不属于成功采集路径。

**限制**：它是逻辑切点，不是整个 JVM、网络、磁盘和异步生成的静止点。`waitUntilNextTick` 的 `runAllTasks` / `managedBlock` 可以推进主线程任务，`MinecraftServer.pollTaskInternal` 还会轮询各维度 chunk task。保存的 `managedBlock` 也可能执行任务。因此“请求排到 server executor”不等于必定落在这个切点；未来实现需要请求登记与明确 hook，不能在任意 `execute` 回调内直接采集。开始保存的切点也不能自动成为整个产物的共同采样时点，需要明确保存期间任务、持久化内容与运行态副本的协调规则。

### NU → NTE 只作近似描述

| 民间术语 | 26.2 可核对的路径 | 边界说明 |
| --- | --- | --- |
| NTE（中继器、命令方块） | `ServerLevel.tick` 中 `blockTicks.tick`，前面还有服务器 command functions、clocks、维度 weather / sleep / tickTime；另有 fluid ticks | 不是整个服务器 tick 的第一项；命令方块报告时间不定义唯一服务器边界 |
| BE（活塞启动、音符盒） | `runBlockEvents` | 在 chunkSource 后、实体前；不能推断返回时事件队列必空 |
| EU | `entityTickList.forEach` / `tickNonPassenger` / passenger tick | 正常返回后无需保存迭代中的 map 副本或调用栈；实体自身暂态仍存在 |
| TE | `tickBlockEntities` | 在实体之后；ticker 成员、顺序与 pending 注册并不因此持久化 |
| NU（玩家操作） | `PacketUtils.ensureRunningOnSameThread` 将异线程包交给 `PacketProcessor`，在 `processPacketsAndTick` 开头处理；维度之后另有 `tickConnection` / listener tick、player 管理 | 不能把尾部 connection tick 当作全部玩家操作处理；网络到达和排队与逻辑 tick 并发 |

民间阶段是解释部分红石/玩家操作的近似模型，本文使用实际方法路径定义切点。命令方块打印的 gametime 与完整服务器循环标识也应分别记录，不能用“打印时间 + 1”代替阶段证据。

`PacketProcessor.processQueuedPackets` 在本版没有数量或时间限额，循环到当时队列为空；并发到达可在它返回后继续排队。末尾切点处仍可有等待下一轮的包。它不是输入截断或网络队列清空屏障；第一阶段不复制 socket、包队列或任意在线玩家输入历史。涉及玩家操作的实验应记录并重放明确输入，或选择不依赖尚未处理输入的起点。

### Fabric hook 与暂停路径

另实查本机 `fabric-api 0.161.0+26.2` 内 `fabric-lifecycle-events-v1 4.1.4+29b6eb019e` 的 `MinecraftServerMixin`：`START_SERVER_TICK` 注入在 `tickServer` 调用 `tickChildren` 之前，**不是 `tickServer HEAD`**；`END_SERVER_TICK` 是 `tickServer TAIL`。后者在正常路径已完成所有维度和 autosave，但仍在 `tickFrame.end` 之前。`IntegratedServer.tickServer` 在 `super.tickServer` 之后还可调整 view/simulation distance；因此该 Fabric event 不等于完整 integrated 处理返回。其他同一 event 的 listener 顺序也需要记录。这是版本固定的 hook 证据，不是对未来 Fabric 版本的承诺。

`IntegratedServer.tickServer` 在未暂停→暂停时调用 `saveEverything(false, false, false)`；暂停时改走 `tickPaused`（connection tick 与玩家统计），不推进正常 world tick。`processPacketsAndTick` 仍先处理排队包。专用服 empty-pause 也可提前返回而只做连接维护。因此原生循环边界在暂停态仍存在，但不代表世界模拟推进了一刻；hook、产物与验收需标注正常/冻结/暂停。反复 Esc 触发保存确有本版路径依据，不能认为暂停是纯粹时间停止。

## 保存、卸载、加载的关键路径

### 普通保存副作用已接受，但不是一致性屏障

**实查**：`MinecraftServer.saveEverything` 先保存玩家，再进入 `saveAllChunks`；后者逐维度调用 `ServerLevel.save`，保存 scoreboard/world data/server saved data。`ServerLevel.save` 分别保存 level saved data、chunks、entity storage。

`flush = true` 的两个下游尤其需要注意：

1. `ChunkMap.saveAllChunks(true)` 在等待可保存 chunk 时调用 `mainThreadExecutor.managedBlock`，刷新可访问性，之后调用 `processUnloads(() -> true)`，再同步写入。`processUnloads` 移动待丢弃的 holder、执行卸载队列；`scheduleUnload` 最终调用 `LevelChunk.setLoaded(false)`、`ServerLevel.unload`。
2. `PersistentEntitySectionManager.saveAll` 循环调用 `processPendingLoads`，并对 visibility 为 `HIDDEN` 的 chunk 执行 `processChunkUnload`；该路径对实体设置 `UNLOADED_TO_CHUNK` 并清除 level callback。非 flush 的 `autoSave` 也会处理隐藏区块的实体卸载。

**推断**：`save-all flush` 不是“只读世界状态并等待磁盘”的原语。它可能推进待加载、待卸载和主线程任务。该类正常保存副作用当前接受，应记录保存方式并在干净起点验收；不承诺任意时点保持采集前全部状态。不能为了获得分叉另行主动卸载/重载源服，也不能声称选定 tick 切点自动消除了保存副作用。

`ChunkMap.save` 还会调用 POI flush、`tryMarkSaved`、记录写入状态；这种生产保存路径与向独立产物序列化需要区分。第三方 `saveAdditional` 回调是否有副作用，不能由原版名称推定。

### 保存是分组件捕获、异步编码与写入

**实查**：`ChunkMap.save` 先 `SerializableChunkData.copyOf`，再在 background executor 中 `data.write`，之后写 storage。`copyOf` 复制 section/light/heightmap 等数据并收集 BE NBT、计划刻。`IOWorker.store` 维护 pending writes；同一位置后续写入可替换 pending data；`synchronize` 等待当前 pending writes 并可 flush 存储。

**推断**：直接复制仍在运行的 region/entity/POI 文件不能证明同一时点一致，磁盘完成也不能证明 chunks、entities、saved data、玩家和运行态来自同一个逻辑时点。已有磁盘副本可作为未加载数据的基线，但需要与加载中的内存版本及异步任务协调。原版没有在本次路径中提供跨全部存储的只读事务。

### 卸载确实丢弃并重建运行对象

**实查**：`ServerLevel.unload` 清理 BE、注销 tick container；实体管理器卸载实体并移除回调。加载时 `SerializableChunkData.read` 创建 chunk/tick containers，`LevelChunk` 重建 BE、listeners、tickers；实体 storage 读取递归 NBT，实体管理器根据 section visibility 决定 tracking/ticking，`ServerLevel.EntityCallbacks.onTickingStart` 加入 `EntityTickList`。

**推断**：普通存档可以重建持久化内容，但重建顺序、暂态集合和构造器初始化不等于源服内存。源服不额外主动 unload/reload；保存引起的正常维护副作用则按上述边界接受。目标分支可以从文件启动，再补齐实验需要的运行态。

| POI / scoreboard /其他 saved data、datapack | 独立存储/配置，保存路径不止 chunk与entity | 实体 NBT snapshot 不能替代完整分支文件与注册表/环境 | **实查** `MinecraftServer.saveAllChunks`、`ChunkMap.save`；**待验**完整产物范围 |
| Carpet / 第三方 Mod | 本次没有对每个版本的 mixin、脚本 host、scheduler、static cache 建立持久化闭包 | 规则文件可能保存，运行脚本变量/任务不据此得到保证；不能声称任意 Mod 无损分叉 | **待审计/待验**须记录版本、配置及状态适配范围 |

## NBT + summon 的可用范围

**实查**：`SummonCommand` 的带 NBT 分支设置 `finalize = false`，将 NBT copy 后写入类型 id，用 `EntityType.loadEntityRecursive` 加载，并 `tryAddFreshEntityWithPassengers`。它不走无 NBT 分支的 `Mob.finalizeSpawn`。因此用完整 NBT 逐 root 重建是有源码依据的候选，不必先开发专用实体重建协议。

仍需满足的条件：

- 源实体类型可 summon，分支注册表/Mod 与其相容；和平难度等检查可能拒绝。
- 先处理分支中重复 UUID；操作只影响分支，不删除源服实体。
- 在正确维度使用原坐标；summon 会通过 snapTo 覆盖 Pos，不能假设任意命令位置等价。
- 有骑乘树时仅 summon roots，保留嵌套 Passengers，不再独立召回同一乘客。
- 恢复期间避免分支先运行实验；即使按源列表依次 summon，实体进入 ticking 的时机和 passenger tick 行为仍需验收。
- 对研究相关的跨实体引用、载具/玩家关系和子类字段，恢复后读回验证。

它能恢复上述持久化字段和可加载的子类数据，并可在受控条件下用召回顺序重建目标实体 tick 顺序。它**不单独恢复**世界方块/BE、事件/计划刻全局序、加载集合、独立 random、基础 tickCount 或未编码暂态。需要补这些状态不等于必须放弃 summon。

## 现有 snapshot 的实际覆盖

历史比较基线 `ServerCore`：选定维度，读取 `EntityTickList`，写实体 NBT、顺序及恢复信息；meta 记录顺序 hash、服务器 tick、路径和玩家摘要。`snbtOf` 调用 `Entity.saveWithoutId`。已合并的接口精简去掉重复字段和半径筛选，但没有因此成为世界分叉接口：实体导出仍不调用 world save，也不导出 chunks/POI/saved data。

正式 Go CLI / daemon 的 `protocol.Tools` 将 `fork`、`restore`、`verify`、`order` 明确标为 unsupported，尚不提供本文讨论的完整世界产物拉取和恢复。旧 Python 本地文件复制与 summon 路径是历史实现，不能把它的存在当作无侵入分叉目标已完成。后文列出的能力均是候选。

有四个范围边界不能隐藏：

1. tickList 仅含 ticking 实体，不代表维度中所有 loaded 实体，更不代表磁盘中未加载实体。
2. `tickOrder` 过滤 `isRemoved` 和 `!isAlive`；死亡中但仍有行为/数据的实体可能被排除。“全实体”承诺不成立。
3. snapshot 排除 ServerPlayer，只留姓名/UUID/位置摘要；这不是玩家运行态快照。每个非玩家 passenger 仍写记录，但 root NBT已含乘客，restorable 指示恢复应跳过独立 passenger summon。
4. meta 的 tick 来自 `server.getTickCount()`，不是统一分叉时点或各维度 gameTime。顺序 hash 只能验证被选中实体的 UUID 序列，不能验证世界分叉完整性。

因此现有产物应称为“指定范围的实体 NBT 与 tick 顺序导出”。保留一个通用 NBT 能力合理；便利筛选不是无侵入世界分叉的核心进度。

## 支持边界与实验方法论

以下是后续实现与验收约束，不是本次已完成的功能：

- 用户接受 `save-all` 的侵入，采集可以使用正常保存/flush及其维护副作用；主动 unload/reload、强制加载新源服区块、添加采集票据、替换源实体或改变实验规则不是为此自动获准的操作。正常保存和额外改造源服应区分，也不把“无侵入”解释为零CPU/IO开销或零暂态变化。
- 第一阶段采用完整服务器tick处理返回处的候选边界，不支持在NTE/BE/EU/TE执行中间恢复调用栈，不承诺所有后台任务、网络或Mod都静止。暂停/冻结时标注世界模拟是否推进；网络输入与server tick/gameTime不是同一时间轴。
- 对保存敏感、自动保存参与因果或依赖未覆盖暂态的实验，从更早的干净起点建立分支；验证保存与重载不会破坏相关条件，再在分支重放触发操作及推进刻数。反复Esc触发保存可作为实验操作，而不是采集器必须在其任意中间态无损分叉的要求。若找不到已验证起点，应报告该实验尚不支持，而不是静默声称完整。
- 在选定边界规避实体遍历、计划刻当前执行队列和同步邻居链；仍覆盖或明确限制跨tick的事件、pending注册、顺序、随机源与加载集合。是否需要补齐某项由实验依赖与基线验证决定，不能仅凭表中“有差距”要求复制全部对象。
- 主线程上取得独立数据副本之后才异步编码/传输；不能让后台线程直接遍历可变世界对象。每种复制/序列化回调还需核对只读性和所有权。
- 内存产物、保存期间执行的任务、未加载数据基线、异步pending版本和注册表/配置必须有明确的一致性规则。接受保存副作用不能替代这个规则。失败不能产生伪成功分支；完整性清单和临时产物提交方式应可验证。
- 分支恢复过程可以改变分支；在恢复屏障释放前控制其提前模拟。源服保护与分支保真是不同验收项。
- Mod、玩家、维度或状态未覆盖时，产物明确列出限制。不要用 snapshot数量/orderHash相等声称无损续演。

## 最小能力候选与验证顺序

候选是职责，不固定 CLI 命令名或协议形状：

1. **能力与覆盖说明**：26.2/Mod/注册表环境、维度/采集范围、阶段、已保留/重建/未支持状态。
2. **tick边界采集与产物闭合**：在明确服务器逻辑切点协调正常保存与必要运行态副本；声明保存及任务维护副作用，确定两者的一致性规则，不为采集主动unload/reload源服。这里不预设先保存或先复制的顺序，尤其不能忽略保存等待期间执行的任务。
3. **搬运与本地使用**：CLI可靠带回产物、验证完整性，Agent用本地JDK/文件/Mod/脚本自由构建分支。
4. **分支恢复与屏障**：先支持明确范围的NBT/summon与世界文件恢复，再按差距表补实验必要状态；恢复操作只作用于分支。
5. **可解释验证**：状态差距报告及未改动基线的首个行为分歧，服务实验有效性，不追求虚假的全对象相等。

推荐先验证26.2正常tick边界定位（含多维度、暂停与冻结标记），再验证静态世界、单实体、骑乘树/跨根关系、BE顺序相关装置、跨区块同刻计划刻、跨tick block events、随机行为和加载边界。每种场景记录保存前后变化、实际采集阶段、保存副作用、分支恢复状态及首次续演差异；增加从干净起点重放保存敏感操作的案例。再加入玩家和明确版本的Carpet/其他Mod。

后续实现需验收明确hook在Fabric/Mod注入后的实际顺序、保存期间任务协调、产物搬运及恢复屏障；按被支持实验补子类暂态、lighting/worldgen/mailbox与Mod适配。源码表确定了边界与差距类别，并不要求先实现所有运行态迁移。本文更新不实现新的fork命令，也不声称当前snapshot已在推荐原生切点运行。
